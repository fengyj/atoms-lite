# atoms-lite 需求与设计

## 1. 文档目标

atoms-lite 是一个面向单用户的对话式创作平台。用户通过自然语言描述需求，智能体在隔离工作区中读写代码、执行命令、运行验证并启动预览，最终交付可运行的小型 Web 应用，以及 PPT 等结构化文件产物。

本文定义 atoms-lite 的产品目标、功能范围、架构边界、数据设计、运行方式和验证标准。本文不包含开发排期或开发任务拆解。

## 2. 产品目标

atoms-lite 应形成一个真实、可恢复、可验证的创作闭环：

> 新建项目 → 描述需求 → 智能体修改代码 → 运行与测试 → 预览 → 继续迭代 → 保存版本 → 导出或发布

设计优先级如下：

1. 智能体能够通过工具真实改变项目。
2. 项目、会话和产物能够持久化并恢复。
3. 生成结果能够实际运行，而不是仅返回代码文本。
4. 预览、版本和发布状态相互独立。
5. 保持生成物简洁，并尽量减少对 atoms-lite 平台的依赖。
6. 简单任务支持直接的单角色对话，复杂任务可切换为多角色协作。
7. 用户不提供详细视觉要求时，生成物仍应具有专业、精美、有质感的默认设计。

## 3. 使用范围

### 3.1 支持的应用类型

atoms-lite 不考虑多用户协作、工作区成员、权限邀请或跨用户资源共享，但支持同一用户创建和维护多个项目、会话和产物。

初期面向复杂度可控的产物，包括：

- 单页或少量页面的前端应用
- 表单、列表、详情和简单筛选
- 基于 SQLite 的增删改查
- 小型业务工作流
- 简单 API 和文件处理
- 五子棋、计分工具等轻量交互游戏
- 任务看板、知识列表、个人管理工具等小型应用
- PPTX 等可下载、可预览或可在文件窗口查看的结构化文档
- 传统全栈应用或被约束的 Serverless 应用

平台支持多个独立会话。在同一项目下，不同会话可以分别尝试不同方向；会话应与其对应消息、工具调用、版本和产物关联。

### 3.2 暂不纳入

以下能力不作为核心范围：

- 外部服务连接器和 OAuth
- Theme 系统
- SEO 助手
- 广告和数据分析平台集成
- 复杂多租户系统
- 多用户协作、共享工作区和团队权限
- 大规模高并发应用
- 实时协同编辑
- 任意语言和任意框架生成
- 用户未要求时的多平台部署适配

这些限制不阻碍为未来扩展保留清晰接口。

### 3.3 能力分级

atoms-lite 对用户需求使用三种能力判定：

1. **明确支持**
   - 单用户或小规模应用的常规页面和业务流程
   - 表单、列表、看板、详情、筛选和简单状态机
   - SQLite CRUD 和基本数据迁移
   - 单页面游戏、工具型应用和演示应用
   - PPTX、图片、压缩包等可生成、预览和下载的产物
   - 增量修改、构建、测试、预览、版本和回滚

2. **条件支持**
   - 用户认证、订单、购物车、库存等常见业务功能，但仅作为受控范围的演示或小规模应用
   - 需要第三方数据库、对象存储或模型服务的应用
   - Cloudflare、Vercel 或传统服务器部署适配，但只实现用户明确指定的目标
   - 外部服务集成，前提是用户提供已授权的接口或采用模拟适配器
   - 多页面、较多数据表、复杂权限规则和长流程，需先确认范围后裁剪

3. **当前超纲**
   - 百万级用户、高并发和高可用承诺
   - 生产级支付、财务结算、合规审计或真实敏感交易
   - 复杂电商 ERP、库存同步、物流和供应链
   - 多租户 SaaS 和组织权限体系
   - 大规模分布式系统、消息驱动架构或自建数据基础设施
   - 任意安全测试、互联网爬取或不受限制的代码执行
   - 未提供凭据时操作真实第三方账户

“支持生成购物页面”不等于“支持生产级电商平台”。atoms-lite 可交付商品展示、分类筛选、购物车和演示订单，但不自动承诺真实支付、库存一致性、反欺诈、合规、税费和百万用户承载。

## 4. 核心概念

### 4.1 项目

项目是生成应用的长期容器，包含：

- 项目基本信息
- 当前源码版本
- 会话
- 生成版本
- 预览状态
- 发布或导出记录
- 运行配置

### 4.2 会话

会话保存用户与智能体围绕项目进行的连续工作，包括：

- 用户消息
- 智能体消息
- 状态事件
- 工具调用和结果
- 运行或构建日志
- 需要用户确认的请求
- 与本次会话关联的版本

重新打开项目时，应能恢复上下文并继续工作。

同一项目可以拥有多个会话。默认打开最近使用的会话，但用户应能新建、切换、重命名和删除会话。多个会话不自动合并工作结果，所有文件变更通过明确的版本关系记录。

### 4.3 版本

版本是项目文件在某一时刻的持久化快照。它应具备：

- 唯一标识
- 父版本
- 来源会话和消息
- 文件清单与摘要
- 保存时间
- 验证状态
- 可回滚状态

预览版本、已验证版本和已发布版本是不同状态，不应自动混同。

### 4.4 工作区

工作区是 Sandbox 中实际运行的项目文件目录，例如 `/workspace`。工作区是可替换的计算环境，不是唯一可信存储。

持久化快照和版本存放在 R2；Sandbox 中的文件可能在空闲停止后丢失，并应根据持久化版本恢复。运行配置与 workspace 一起描述项目如何重新启动，而 Agent checkpoint 独立保存在会话状态存储中。

### 4.4.1 Git 与平台版本

工作区应初始化为 Git 仓库，用于记录文件差异、阶段提交、会话分支和回滚。Git 是工作区内的源码版本机制，但不是 atoms-lite 唯一的版本存储。

三者职责如下：

- **Git commit**：工作区内一次原子化源码变更，方便生成 diff、比较状态和恢复。
- **D1 版本记录**：保存版本、会话、父版本、Git commit、验证状态和 R2 快照之间的关系。
- **R2 快照**：保存可跨 Sandbox 恢复的整个工作区，是容器回收后的持久化基础。

用户无需理解 Git；平台将 commit 显示为普通版本。每个用户可见版本至少对应一个有效 commit 和一个可恢复快照，不能仅依赖容器临时 `.git` 目录。

Agent 可以通过 `git status`、`git branch` 和 `git log` 查看当前分支、未提交变化和 HEAD。平台也可以读取这些信息用于展示，但平台在 Sandbox 停止后不能直接访问工作区，因此仍需要在 D1 保存当前会话对应的版本和 Git commit。D1 中的指针用于决定“启动后恢复哪个快照”，Git 用于检查和操作“恢复后实际工作的内容”。

Git 默认只使用本地仓库，不自动创建 GitHub/GitLab 仓库，也不向外部远端推送。若未来增加源码同步或连接器，应作为明确启用的独立能力。

### 4.5 产物

产物是会话或版本产生的可交付结果，不限于源码。例如：

- 可运行的 Web 应用
- PPTX 或其他文档文件
- 图片、数据文件或归档
- 构建日志和验证报告
- 导出 ZIP

产物应保存类型、名称、来源版本、创建时间、R2 地址、可预览方式和下载状态。

## 5. 功能需求

### 5.1 项目管理

用户可以：

- 创建、查看和重新打开项目
- 为项目设置名称和描述
- 查看项目当前版本和状态
- 删除项目及其相关产物
- 导出项目源码

### 5.1.1 单用户模型

atoms-lite 以单机或单租户式部署假设运行，不实现注册、邀请、团队权限或多人协作。认证不是核心能力；如部署环境需要访问保护，可通过部署层的简单访问控制实现，不引入产品化的用户管理系统。

### 5.2 对话交互

用户可以：

- 输入自然语言需求
- 上传需求附件
- 查看智能体的阶段性状态
- 查看工具调用、运行结果和失败原因
- 取消正在运行的操作
- 对需要确认的危险操作进行批准或拒绝
- 中断并在之后继续会话
- 新建、切换、重命名和删除会话
- 在不同会话中保留相互独立的需求与版本分支
- 在多角色模式中通过 `@角色名` 指定接手者
- 查看角色列表、角色职责及当前角色状态

消息和事件必须支持流式返回，长时间任务不得占用单次前端页面请求。

`@` 仅表示消息的目标角色，不代表创建新的会话。用户可以通过 `@builder`、`@visual` 或 `@verifier` 等标识直接提出任务、追问和复核要求。被指定角色处理时，Coordinator 仍负责维护共同目标、上下文与最终完成判断。

### 5.2.1 会话命令

输入框应支持自然语言和以 `/` 开头的会话命令。命令是明确的产品操作，不应与普通需求混淆。

建议支持：

- `/help`：查看当前模式下可用命令。
- `/status`：查看 Agent、角色、Sandbox、预览和版本状态。
- `/compact`：压缩当前上下文，保留完整历史。
- `/stop`：停止当前运行和未执行完的后续步骤。
- `/retry`：从最近失败阶段重试，而不是重建整个会话。
- `/reset`：结束当前执行并清除未持久化的运行状态；不删除已保存会话、版本和产物。
- `/undo`：对最近一次已提交代码变更创建反向版本，不改写 Git 历史。
- `/version`：查看或切换当前基础版本。
- `/preview`：启动、停止或刷新预览。
- `/role`：切换单角色/多角色模式或查看当前角色。
- `/scope`：重新展示当前可交付范围、假设和超纲项。
- `/export`：导出当前版本、源码包或指定产物。

高风险或不可逆命令必须先展示影响范围并请求确认。删除会话、删除版本、还原旧版本与重置运行状态不应使用含义相同的命令名称，以免用户混淆。

常用操作同时提供按钮或菜单，不要求用户记忆命令。未知命令应明确提示，而不是作为普通自然语言发送给模型。

### 5.3 智能体执行

智能体能够根据现有项目：

- 理解需求
- 检查项目结构和当前文件
- 制定修改步骤
- 修改现有代码
- 安装依赖
- 运行验证命令
- 根据错误进行修复
- 启动和停止应用
- 保存一个可追溯版本

平台提供两种协作模式：

- **单角色模式**：由一个协调/执行角色直接理解需求、调用工具和交付结果，适合五子棋、任务看板、PPT 等目标明确的简单任务。
- **多角色模式**：由协调者按阶段组织专家角色，适合需求较复杂、需要产品设计、工程实现、视觉审核和结果验证的任务。

多角色模式不意味着所有角色必须并行执行。系统可以按顺序或在互不冲突的步骤中并行，并始终保持统一的项目状态和完成标准。

#### 5.3.0 多角色扩展边界

第一阶段即使只启用单角色，也应将角色作为稳定边界引入。消息、工具调用、模型请求和 UI 事件不得直接假定“整个会话只有一个无身份的 Agent”。

核心契约包括：

```ts
interface RoleDefinition {
  id: string;
  name: string;
  description: string;
  systemPromptRef: string;
  allowedTools: readonly string[];
  modelProfile?: string;
}

interface RoleInvocation {
  runId: string;
  sessionId: string;
  roleId: string;
  objective: string;
  contextRefs: readonly ContextRef[];
  targetVersionId?: string;
}

interface RoleResult {
  roleId: string;
  status: "completed" | "handoff" | "needs_input" | "failed" | "stopped";
  summary: string;
  nextRoleId?: string;
  artifactRefs?: readonly ArtifactRef[];
  toolResultRefs?: readonly ToolResultRef[];
}

interface RoleOrchestrator {
  start(input: StartSessionInput): Promise<RoleInvocation>;
  next(input: RoleTransitionInput): Promise<RoleInvocation | null>;
}
```

这些类型是产品层协议，不能直接以 Cloudflare `subAgent()`、`agentTool()` 或某个模型 SDK 类型作为公共接口。具体 SDK 只负责实现某个 `RoleOrchestrator` 或角色运行器。

第一阶段可以使用 `SingleRoleOrchestrator`：

```text
用户消息
  ↓
coordinator 角色
  ↓
模型与工具循环
  ↓
完成、审批或失败
```

后续多角色模式可替换为 `MultiRoleOrchestrator`：

```text
用户消息
  ↓
Coordinator 调度
  ├── Product
  ├── Builder
  ├── Visual
  └── Verifier
```

切换编排器不应改变消息协议、Sandbox 工具接口、版本模型或前端事件格式。

角色实现还应满足：

- 所有消息至少包含 `authorRole`；定向消息包含 `targetRoles`。
- 模型和工具事件至少包含 `runId`、`roleId` 和 `sessionId`。
- 工具注册表是全局的，角色只通过 `allowedTools` 获得子集。
- 所有角色共享同一 Sandbox、Git 仓库和版本模型。
- 角色之间通过结构化 `RoleResult` 交接，不传递隐式自由文本状态。
- `@角色` 产生定向调度请求，但最终仍由 Coordinator 检查角色能力和当前阶段。
- 第一阶段不要求角色独立 Durable Object；后续是否使用 `subAgent()` 是运行器实现选择。
- 写文件和执行构建的角色默认串行持有 workspace 写锁。

消息历史继续由 Agents SDK/AIChatAgent 管理。atoms-lite 不修改框架消息表，只使用 `atoms_` 前缀的业务表保存角色元数据、角色状态、摘要和调度事件。消息 ID、run ID 和 role ID 建立关联。

可选角色包括：

- 协调者：决定下一步和完成条件
- 产品角色：在需求不明确时澄清
- 开发角色：实现页面、API 和数据逻辑
- 验证角色：运行构建、测试和健康检查
- 视觉角色：检查布局、层级、响应式表现和默认视觉质量

角色之间共享统一的项目状态、工具权限和事件协议。最终向用户展示的是当前阶段、参与角色和结果，不把内部提示词或无关推理过程作为产品内容。

#### 5.3.1 角色寻址

多角色模式支持以下交互：

- `@角色`：明确要求某个角色响应当前消息。
- `@coordinator`：要求协调者重新规划、总结状态或决定下一步。
- 无 `@` 消息：由协调者判断是否继续当前任务、唤醒某个角色，或由默认角色响应。
- 同时指定多个角色时，应先转换为有顺序的子任务，不允许多个角色对同一工作区进行无序并发修改。

角色名称应支持自动补全，并显示对应职责。未知角色或当前模式下不可用的角色需要明确提示，不得静默转发给错误角色。

#### 5.3.2 会话历史与角色历史

每个项目会话维护一份全局主历史。该历史保存用户消息、角色消息、工具调用、交接结果、审批和产物关联，是整个任务的可信记录。

每个角色同时拥有独立的上下文视图，包括：

- 直接发送给该角色的用户消息
- 该角色处理过的任务
- 分配给该角色的上下文摘要
- 该角色的阶段结论
- 该角色依赖或产生的工具结果
- 来自其他角色的显式交接

因此，角色历史在上下文和界面视图上是独立的，但底层数据不完全物理隔离。所有角色消息仍属于同一个主会话，并通过 `authorRole`、`targetRoles`、`handoffId` 等字段建立关系。

角色不会自动读取全部完整对话历史，而是由 Coordinator 提供任务所需的共享上下文，以避免不同角色提示词无限增长、角色职责混乱及敏感内部内容泄漏到不需要的角色。用户可以切换“全部对话”和“角色视图”；角色视图只过滤和聚合，不删除主历史。

当用户通过 `@` 与角色沟通时，该消息：

1. 写入主会话历史。
2. 标记为该角色的定向消息。
3. 出现在该角色上下文视图中。
4. 在模型调用时由 Coordinator 补充必要的项目状态和前置结论。
5. 角色回复再次关联到原消息和当前版本。

切换角色不会自动创建新会话，也不会复制项目工作区。只有用户明确创建会话时才建立新的会话历史和版本分支。

#### 5.3.2.1 会话上下文压缩

压缩属于模型上下文管理，不属于历史删除。每个项目会话保留：

```text
原始消息和工具事件
  ↓
会话级摘要
  ↓
角色级摘要
  ↓
当前调用使用的短期上下文
```

原始消息、工具结果、审批、Git 版本和产物关系均永久保留在平台历史中，压缩只生成可替代旧消息进入模型上下文的结构化摘要。

多角色模式中：

- Coordinator 维护会话级摘要，包含用户目标、约束、已决定事项、未完成项和关键版本。
- 每个角色维护自己的角色摘要，包含该角色任务、结论、依赖、工具结果和交接内容。
- `@` 消息、角色输入和角色输出仍写入同一主历史。
- 角色被唤醒时，模型输入通常包含“用户目标 + 会话摘要 + 本角色摘要 + 交接内容 + 最近必要消息”，不默认输入所有角色的完整历史。
- 角色摘要可独立更新，但不得私自改变会话级目标、范围确认和用户约束。

单角色模式只需要会话级摘要，不维护没有意义的多角色摘要。

压缩可由以下条件触发：

- 上下文接近模型预算阈值
- 工具输出量过大
- 用户执行 `/compact`
- Coordinator 完成一个较长阶段
- 角色等待时间较长但需要恢复工作

摘要至少保存：

- 用户目标和验收条件
- 已接受的假设与超纲项
- 设计与架构决定
- 已执行的关键操作
- 当前文件或版本
- 失败原因和未解决风险
- 当前产物状态
- 下一步计划

工具原始输出不应整段进入摘要；摘要保存结果、路径、退出码和必要错误，详细日志继续引用 D1 或 R2 中的记录。压缩需记录来源消息范围、生成时间和所用摘要版本，用户可查看摘要，但摘要更新不会删除原始消息。

每次压缩完成后，新模型调用应能只依赖：

- 最近未压缩消息
- 会话摘要
- 当前角色摘要
- 当前工作区和版本状态

就恢复后续工作。

### 5.3.3 需求准入与预期管理

在产生代码前，Agent 应先对需求进行准入判断，将结果分为：

- `in_scope`：可直接执行。
- `in_scope_with_assumptions`：可执行，但必须公开默认假设。
- `needs_clarification`：需要用户补充目标、运行规模或关键外部依赖。
- `partial_scope`：可交付一部分，并明确暂不实现内容。
- `out_of_scope`：当前能力不能可靠交付，不应开始伪装完成。

准入至少检查以下维度：

- 目标产物是 Web、PPT 还是其他文件
- 预期用户数量和并发量
- 是否需要登录、组织或多租户
- 是否涉及真实支付和敏感交易
- 是否依赖第三方账号、API 或凭据
- 是否涉及生产级可用性、灾备和合规
- 是否需要任意框架、语言或现有大型仓库
- 是否要求在指定时间和资源内完成

需求判定应由两层机制共同完成：

1. **确定性策略**：检查能力配置、禁止项、支持的产物类型、工具权限和运行预算。
2. **语义分析**：由 Coordinator 识别模型无法单纯通过关键词判断的规模、集成、风险与隐含依赖。

确定性策略用于约束硬边界；模型用于理解语义。模型不得覆盖明确的安全边界和能力上限，也不得仅因用户措辞自信就宣称生产级能力。

如果需求可以拆分，系统优先提出可交付子范围，而不是直接拒绝。例如：

```text
用户：帮我做个购物商店，支持百万用户。

系统判断：
- 商品展示、筛选、购物车、演示订单：支持
- 登录、支付、库存和外部集成：需要进一步确认
- 百万用户规模、高可用和性能目标：当前超纲，无法仅靠生成代码承诺

建议：
1. 先生成一个可运行的单商店演示版。
2. 使用 SQLite 保存商品和演示订单。
3. 支付先使用模拟结算。
4. 将登录、支付服务、生产数据库、负载测试和容量规划标记为后续要求。
5. 如要进入生产，需要用户明确流量、可用性、支付地区和合规要求。
```

系统对超纲需求的响应应遵守以下顺序：

1. **确认理解目标**：复述用户想实现的核心结果。
2. **说明可交付部分**：给出当前能可靠完成的范围。
3. **说明边界原因**：区分能力限制、凭据缺失、安全风险和规模验证不足。
4. **提出替代方案**：缩小范围、使用模拟服务、交付原型或给出生产化清单。
5. **请求明确选择**：由用户确认降级范围或补充约束。
6. **记录约定**：将接受的范围、假设、未实现项写入会话和产物说明。

Agent 不应：

- 为未验证的并发量给出“支持百万用户”的承诺
- 将模拟支付描述为真实支付
- 把 SQLite 演示数据描述为生产级数据架构
- 在未获得用户确认时擅自删减核心需求
- 在缺少外部凭据时静默使用硬编码或伪造集成
- 将构建成功等同于负载、安全或生产就绪

若用户仍坚持超纲目标，系统可以生成**原型、架构说明和生产化差距清单**，但必须将其与可运行、已验证的交付部分区分展示。

### 5.4 工具执行

智能体通过受控工具操作 Sandbox，至少包括：

- 列出文件
- 读取文件
- 写入或创建文件
- 搜索代码
- 执行受限命令
- 启动和停止进程
- 读取进程日志
- 等待服务端口就绪
- 暴露预览端口
- 创建和恢复工作区快照

所有工具均需接受结构化参数。模型不得获得对底层任意命令、系统目录和平台凭据的无限制访问。

### 5.5 应用预览

用户可以：

- 查看当前运行中的应用
- 启动、停止和重新加载预览
- 查看构建状态和最近日志
- 在不同版本之间切换预览
- 在错误时获得可读提示

预览是项目工作区中的运行结果，不等同于已发布应用。

### 5.5.1 多类型预览

预览窗口应根据产物类型选择渲染方式：

- Web 应用：iframe 和独立地址
- PPTX：封面、页面缩略图或转换后的图片/PDF 预览
- 图片：图片查看器
- 数据或文本文件：只读查看器
- 不支持在线查看的文件：显示摘要和下载入口

不同产物可共存于同一个会话，但预览窗口一次聚焦一个主要产物。

### 5.6 版本和回滚

系统应保存每次有效修改形成的版本，并支持：

- 查看版本列表
- 查看版本描述和来源
- 切换版本
- 回退到指定版本
- 从旧版本继续生成新版本

回滚只改变当前工作版本，不得静默覆盖已发布版本。

Git 版本操作遵循以下规则：

- 项目初始化时创建仓库、默认分支和初始提交。
- 每个修改会话可使用独立分支，分支从会话声明的基础版本创建。
- Agent 需要保留变更前状态，并通过结构化写文件工具或受控 Git 命令修改。
- 一轮修改完成且基础验证通过后，创建用于平台版本记录的 commit。
- 高风险操作前可创建短期 checkpoint commit。
- 切换平台版本时，先恢复对应快照，再校验 Git commit 和工作区清洁状态。
- 回滚优先通过“基于旧版本创建新提交”实现；不得直接要求用户执行强制 reset。
- 同一版本快照不得被修改历史覆盖。

用户看到的是版本列表、来源会话、diff 摘要和验证状态，Git hash 作为可选技术信息显示。

### 5.7 导出和发布

基础交付形式为：

- 导出源码
- 下载指定版本压缩包
- 在 atoms-lite 内运行预览

完整外部一键发布的优先级低于核心创作闭环。架构仍需保存发布记录和目标版本，以便后续接入 Cloudflare 或其他发布方式。

### 5.8 页面结构

atoms-lite 只有两个主要页面：

1. **首页 `/`**
2. **会话页面 `/sessions/:sessionId`**

设置、需求确认、产物下载、版本回退和删除确认等操作均使用会话页中的面板、抽屉、弹窗或内联状态完成，不新增独立的管理页面。

#### 5.8.1 首页

首页采用常见 Agent 工具的聚焦式结构，由以下区域组成：

- 新会话输入区
- Agent 模式选择：自动、单角色、多角色
- 可选附件入口
- 能力范围与主要限制的简短提示
- 示例需求入口
- 历史会话列表
- 会话搜索、筛选和排序
- 会话继续、重命名、删除等上下文操作

新会话输入区不只是单个裸输入框，还应支持多行需求、附件、模式选择和必要的发送控制，但不得引入与创作无关的导航和信息卡片。

历史会话以当前用户的最近工作为中心，显示：

- 会话标题
- 产物类型
- 最近消息摘要
- 当前状态
- 最后更新时间
- 当前版本或产物缩略图

用户发送第一条有效需求后，首页创建会话并进入对应的会话页面。一个需求是否被拆分为多个会话由用户明确创建操作决定，不自动生成额外会话。

#### 5.8.2 会话页面

会话页面是主要工作区，包含：

- **对话组件**：主会话历史、角色视图、`@`、附件、输入、审批、停止和继续。
- **Preview 组件**：当前 Web 应用、PPT 或其他可视化产物的预览。
- **Artifacts 组件**：当前会话和项目产生的源码包、PPTX、图片、日志及其他文件。
- **Sandbox 组件**：文件树、终端输出、进程、构建/测试状态和生命周期信息。
- **版本组件**：查看历史版本、切换预览版本、回退和从旧版本继续。

#### 5.8.2.1 消息与文件渲染

对话消息支持安全的 Markdown 渲染，包括：

- 标题、列表、引用和表格
- 行内代码与多行代码块
- 语言标识、复制、换行和展开
- 文件路径、版本、产物和错误位置引用
- 受控任务清单
- 适度渲染 Mermaid 等结构图

Markdown 必须经过 HTML 清理，不允许消息内容执行任意脚本、提交表单、访问平台内部接口或覆盖工作台。外部链接必须显示目标并使用安全的新窗口策略；图片只允许受控来源或平台附件。

会话页支持查看代码文件，但默认以只读方式呈现：

- 语法高亮
- 行号
- 当前版本标识
- 大文件分页或局部加载
- 文件路径与搜索
- 单文件 diff 和版本对比
- 复制代码与下载文件

代码文件与聊天中的代码块使用同一主题和语言识别规则，但前者来自 Sandbox 或指定版本快照，不能依赖聊天消息中的代码文本。不存在对应文件时，应提示消息代码仅为说明内容，不能冒充已写入工作区。

工具结果可以在对话中显示摘要，在 Sandbox 面板中查看完整日志。终端输出应保留换行、ANSI 色彩的受控转换和截断说明，不能把日志当作可执行 HTML。

#### 5.8.2.2 Agent 与角色状态

会话页面支持查看当前所有已启用角色的状态。角色状态至少包括：

- `idle`：未参与当前工作
- `queued`：已安排但尚未开始
- `working`：正在执行模型调用或工具
- `waiting_for_user`：等待澄清或审批
- `waiting_for_handoff`：等待其他角色结果
- `retrying`：正在重试失败步骤
- `completed`：已完成本轮职责
- `failed`：无法完成，存在明确错误
- `stopped`：运行被用户取消

状态面板可显示：

- 角色名称与职责
- 当前任务摘要
- 所处阶段和耗时
- 当前工具名称
- 产出或失败摘要
- 最新消息链接
- 是否正在等待其他角色
- 与其关联的版本或产物

用户可点击角色进入角色历史视图，但不会显示模型的隐藏推理或内部私有提示词。单角色模式只显示当前 Agent；多角色模式显示 Coordinator 和各参与角色。

用户简述中的“previous 组件”在产品语义上对应 **Preview 预览组件**。历史内容由 Preview 中的版本选择器和独立的版本组件表达，避免把预览与历史列表合并成含义不清的控件。

会话顶部仅显示必要的全局状态：

- 项目与会话标题
- Agent 模式和当前角色
- 运行状态
- 当前版本
- Sandbox 状态
- 返回首页
- 导出当前产物

### 5.9 工作台布局

用户进入会话后，应看到以 atoms.dev 为交互参考的聚焦式创作工作台，而不是普通文档管理或后台管理系统。只借鉴其信息架构、层级和操作体验，不复制其品牌资源或加入与 atoms-lite 无关的增长、连接器和营销内容。

主工作区域至少包含：

- **会话窗口**：查看对话、发送新需求、切换单角色/多角色模式、确认操作和取消运行。
- **预览窗口**：查看当前 Web 应用、PPT 或其他可视化产物。
- **Sandbox 窗口**：查看文件树、运行状态、终端输出、构建/测试结果和资源生命周期状态。
- **Artifacts 窗口**：查看、切换、预览、下载和打开由当前项目生成的文件与产物。
- **版本窗口**：查看来源、时间、验证状态，并切换或恢复历史版本。

窗口可以根据屏幕宽度采用分栏、标签页、抽屉或全屏切换，但这些能力必须始终容易到达。会话窗口是主要入口，预览窗口默认占据主要视觉区域，Artifacts、Sandbox 和版本信息按需展开。

较宽屏幕建议采用三栏结构：

```text
左侧：会话对话
中部：Preview
右侧：Artifacts / Sandbox / 版本标签页
```

较窄屏幕采用对话与 Preview 的主标签切换，Artifacts、Sandbox 和版本通过底部面板或抽屉打开。

工作台应显示但不喧宾夺主的状态：

- 当前项目和会话
- Agent 模式
- 当前角色
- 运行、等待审批、成功或失败状态
- 当前版本
- Sandbox 运行或停止状态
- 当前预览和主要产物
- 当前需求属于明确支持、条件支持或超纲
- 已接受的默认假设与未实现内容

不包含连接器商城、主题市场、SEO 助手、广告、Analytics、团队空间等当前范围之外的导航。

在新建会话时，应以简洁方式展示当前能力范围和主要限制。对复杂需求，Agent 在执行前显示“拟交付范围”卡片，包括：

- 本次将实现的内容
- 采用的默认假设
- 不会实现的内容
- 需要的外部服务或凭据
- 已知技术风险与验证范围

用户确认或调整后再开始高成本执行。

### 5.10 默认设计质量

当用户没有给出 UI 细节时，Agent 仍必须为 Web 应用、PPT 和其他可视化产物应用统一的默认设计标准：

- 清晰的信息层级与稳定的视觉节奏
- 合理的留白、字号、对比度和间距
- 一致的颜色、圆角、边框和阴影语言
- 完整的悬停、聚焦、选中、禁用、加载、空状态和错误状态
- 适当的响应式布局
- 真实可交互，而不是静态展示占位
- 有克制的动效和过渡，不影响可用性
- PPT 页面之间具有一致的母版感、主题和叙事结构

可以使用高质量的默认字体、图标和布局资产，但不得依赖外部闭源模板。若用户提出具体品牌或设计要求，则以用户要求为准；否则不生成粗糙的默认脚手架页面。

设计质量需要在验证阶段检查，而不是仅把“看起来美观”作为提示词措辞。

## 6. 非功能需求

### 6.1 持久化

刷新页面、Worker 重启或 Sandbox 回收后，不应丢失：

- 项目
- 会话与消息
- 工具调用记录
- 当前版本
- 版本历史
- 发布或导出记录
- 生成应用的源码快照

### 6.2 隔离

每个生成项目使用独立 Sandbox 标识和工作区。生成代码不得：

- 读取其他项目文件
- 访问 atoms-lite 的密钥
- 直接修改平台数据库
- 访问平台内部管理接口
- 绕过网络和命令策略

### 6.3 可靠性

长时间运行应具备：

- 可重试的阶段
- 幂等工具写入
- 中断和取消
- 状态恢复
- 显式错误返回
- 输出和日志截断
- 超时与资源限制

不允许通过静默回退制造成功结果。

### 6.4 可观测性

平台需要为项目保存以下执行信息：

- 会话和版本关联
- LangGraph 节点状态
- 模型请求标识
- 模型用量
- 工具调用参数摘要
- 命令退出码
- 构建和预览状态
- 错误类型与消息
- Sandbox 启动和恢复事件

敏感参数和凭据不得写入普通日志。

用户界面可以展示面向用户的简化事件，完整的内部调试日志保留在可选面板中，避免影响对话和预览体验。

### 6.5 可移植性

生成应用默认只满足用户明确提出的技术要求，不主动引入多平台抽象。若用户未提出特殊部署目标，应优先生成普通、直接可运行的 Web 程序。

当需要平台可移植性时，通过最小的运行时和基础设施适配层实现，而不是要求业务代码包含多个平台分支。是否支持 Cloudflare、传统服务器、Vercel 或其他环境，应由项目需求和构建配置决定。

### 6.6 产物体验

不同类型的产物应有统一的生成质量标准，但不强制使用统一技术实现：

- Web 应用支持真实交互和基础可访问性。
- PPT 等文件可下载，并尽量提供页面级预览。
- 小型应用应避免只生成静态 mockup。
- 视觉、文案和功能同时进入完成判定。

## 7. 技术栈

### 7.1 前端

- Next.js
- React
- TypeScript
- Tailwind CSS
- shadcn/ui
- AI Elements

AI Elements 用于显示消息、工具调用、文件结果、执行状态和人工确认。它不负责 Agent 编排。

工作台界面在布局和交互层面参考 atoms.dev：会话、预览、执行环境和产物构成一个连续工作面板，其他后台信息不占据主导航。视觉实现使用项目自己的品牌、图标和资产，不复制 atoms.dev 的专有内容。

前端主路由固定为首页与会话页：

```text
/
/sessions/:sessionId
```

历史会话详情、Artifacts、Sandbox、Preview 和版本不提供各自的独立一级路由，均作为会话页状态或可分享的查询状态呈现。会话页刷新后应根据 URL 和持久化状态恢复当前面板、当前版本和预览目标。

### 7.2 控制面

- TypeScript
- Cloudflare Workers
- Durable Objects
- Cloudflare Workflows
- LangGraph.js

LangGraph.js 负责状态图、节点编排、工具循环、中断、恢复和多角色扩展。

### 7.3 模型服务

OpenCode Go 作为模型服务层，向控制面提供稳定的模型调用接口。至少应支持：

- 文本响应流
- 工具调用
- 请求取消
- 用量信息
- 唯一请求标识
- Provider 路由和错误标准化

控制面不应把模型密钥暴露给浏览器或 Sandbox。

### 7.4 执行环境

生成代码和工程工具运行在 Cloudflare Sandbox。Sandbox 内包含：

- Node.js 和 TypeScript 工具
- 包管理器
- SQLite
- Shell 和基础开发工具
- 预览服务启动能力
- Web 测试与截图能力
- PPTX 或其他文档生成所需的运行时和转换工具

本地开发使用 Wrangler 和 Podman 或其他兼容容器引擎。Cloudflare Containers 应使用真实本地容器启动，而不是仅依赖纯内存模拟。

### 7.5 数据与存储

- D1：平台结构化元数据
- Durable Object SQLite：单会话或单项目执行状态
- R2：源码快照、日志、附件和导出包
- Cloudflare Queues：异步、可重试的后台工作
- SQLite：生成应用在 Sandbox 中开发时的数据存储

生成程序使用哪种生产数据库，应由用户需求和部署目标决定。未要求 Cloudflare 原生部署时，不默认引入 D1 专属代码。

```text
用户浏览器
  │
  ├── Next.js 界面
  └── SSE / WebSocket
         │
         ▼
Cloudflare Worker API
         │
         ▼
Session Durable Object
  ├── LangGraph.js
  ├── 会话顺序控制
  ├── 中断、审批和取消
  ├── 工具权限策略
  ├── OpenCode Go Client
  └── Sandbox Tool Dispatcher
         │
         ├── D1
         ├── R2
         ├── Queue / Workflow
         └── Cloudflare Sandbox
              ├── /workspace
              ├── SQLite
              ├── 构建和测试命令
              ├── 应用进程
              └── 预览端口
```

### 8.1 控制面与执行面

控制面位于 Worker 和 Durable Object，负责：

- 用户请求
- LangGraph 状态机
- 模型调用
- 工具选择和审批
- 状态持久化
- 消息和事件推送
- 版本管理

执行面位于 Sandbox，负责：

- 文件系统
- 代码修改
- 包安装
- 构建和测试
- 数据迁移
- 应用运行
- 预览服务

Agent 本身不在 Sandbox 内运行。Worker 通过 Sandbox SDK 调用隔离后的工具能力。

### 8.2 长时间运行

Session Durable Object 管理单会话顺序、实时消息和取消信号。

Workflow 负责跨步骤的持久执行和恢复；Queue 用于构建、快照、导出和其他可重试后台工作。单次 HTTP 请求不应包揽完整 Agent 生命周期。

同一项目可以保存多个会话，但同时修改同一工作区的写操作必须由项目级执行锁串行化。不同会话可基于相同版本创建独立分支；若同时运行只执行只读分析或独立产物生成，可并行处理。

## 9. Sandbox 工具设计

业务代码只依赖统一的 Sandbox 适配器：

```ts
interface SandboxAdapter {
  ensureWorkspace(project: WorkspaceRequest): Promise<Workspace>;
  list(path: string): Promise<FileEntry[]>;
  read(path: string, range?: LineRange): Promise<FileContent>;
  write(path: string, content: string): Promise<WriteResult>;
  search(query: SearchRequest): Promise<SearchResult[]>;
  diff(from?: string, to?: string): Promise<GitDiff>;
  status(): Promise<WorkspaceStatus>;
  checkpoint(message: string): Promise<GitCommit>;
  exec(command: CommandRequest): Promise<CommandResult>;
  start(command: ProcessRequest): Promise<ProcessHandle>;
  stop(processId: string): Promise<void>;
  logs(processId: string, options?: LogOptions): Promise<ProcessLog[]>;
  expose(port: number): Promise<PreviewEndpoint>;
  snapshot(options?: SnapshotOptions): Promise<Snapshot>;
  restore(snapshotId: string): Promise<void>;
}
```

生产环境使用 `CloudflareSandboxAdapter`。本地开发可使用 Podman 实现相同接口，以降低开发和测试成本并验证容器兼容性。

命令接口应优先采用程序和参数数组，例如：

```ts
{
  program: "npm",
  args: ["run", "build"],
  cwd: "/workspace",
}
```

它不应默认把模型生成的任意 Shell 字符串直接传给执行器。

`git diff`、`git status`、`git show`、`git commit`、受控 `switch` 等操作可通过专用工具执行。模型不应直接运行 `git reset --hard`、强制覆盖、任意 remote 操作、rebase 或改写已保存历史。推送、拉取和远端认证不属于核心 Sandbox 能力。

## 10. Sandbox 生命周期

### 10.1 懒启动

创建 `getSandbox()` 客户端句柄不应立即启动容器。仅在第一次文件操作、命令执行、进程启动或端口暴露时启动 Sandbox。

打开对话但没有工具需求时，不需要创建运行中的容器。

### 10.2 空闲停止

Sandbox 应配置 inactivity timeout。一定时间未收到文件、命令、预览或进程请求后，容器可以停止。

停止容器不删除项目；D1 和 R2 中的元数据、会话、版本及源码仍然保留。

### 10.3 初始化

首次启动的 Sandbox 初始目录应包含：

- atoms-lite 提供的基础工具
- 空的 `/workspace`
- 平台运行时
- 受控命令和网络策略

项目文件不由容器镜像永久保存，而是从指定版本恢复。

R2 快照在以下时机生成：

- Agent 完成一轮有效修改后
- 用户创建可见版本时
- Sandbox 准备因空闲停止时
- 导出或发布前
- 高风险操作前用于短期恢复

首次启动或重新打开会话时可按 D1 中的会话版本记录直接恢复对应快照；不要求 Agent 先启动一个空 Sandbox 再自行猜测应该使用哪一个版本。

快照默认包含整个 `/workspace`，包括源码、`.git`、SQLite 数据库、资源文件和非敏感项目运行配置。可排除 `node_modules`、构建缓存、日志和其他可再生内容。

项目运行配置应可随项目保存和恢复，例如：

```json
{
  "runtime": "node",
  "command": "npm run dev",
  "cwd": "/workspace",
  "port": 3000,
  "environment": {
    "NODE_ENV": "development",
    "DATABASE_PATH": "data/app.db",
    "LOG_LEVEL": "info"
  },
  "secretRefs": {
    "API_KEY": "secret:project-api-key"
  }
}
```

普通、非敏感的环境变量及其默认值可以保存到 R2 中的项目运行配置。密钥只保存 Secret 引用；真实密钥由平台 Secret Store 持有，并在启动进程时注入。系统识别到 API key、token、password、credential 等疑似敏感字段时，不应将明文写入 Git、manifest、D1 日志或 R2 快照。

manifest 不是环境变量备份，也不是另一套用户可见版本。它只记录快照的身份和校验信息，例如：

```json
{
  "versionId": "v_123",
  "gitCommit": "9c4a...",
  "archiveHash": "sha256:...",
  "createdAt": "..."
}
```

其中同类信息也可保存在 D1。manifest 放在 R2 快照旁或随备份保存，是为了在恢复时校验归档完整性并减少对平台当前记录的依赖；如果 R2 归档内没有 manifest，并不影响工作区内的应用运行。

运行时所需的环境变量和启动参数由项目配置提供，并在启动 Sandbox 时注入。Secret 引用在平台控制面解析为临时环境变量，原始密钥不写入 workspace、Git、D1 日志、manifest 或 R2 快照。应用如果自身需要 `.env.example` 等非敏感模板，可以由源码管理。

除 workspace 文件外，Sandbox 恢复还应考虑以下状态：

- 项目启动命令、工作目录、runtime 和包管理器
- 非敏感环境变量和 Secret 引用
- 应用监听端口和健康检查配置
- Preview 是否需要在恢复后重新启动
- 当前运行的服务定义
- SQLite 数据和迁移状态
- 当前会话使用的 Git commit 或版本
- Agent/LangGraph checkpoint、待审批项和取消状态

不同状态使用不同存储，不能全部塞入 workspace archive：

```text
R2 workspace snapshot
├── 源码和 .git
├── SQLite 数据库
├── 资源与产物
└── 非敏感项目运行配置

D1 / LangGraph checkpointer
├── 会话和消息
├── Agent checkpoint
├── 角色摘要
├── 审批与运行状态
└── Preview 重启配置

Secret Store
└── 密钥明文
```

进程 PID、临时主机名、socket 和公网预览地址不属于可迁移状态。Sandbox 恢复后，应根据保存的服务定义创建新进程和新预览地址，而不是恢复旧 PID 或 URL。

恢复时应同时恢复项目文件、Git 历史和 SQLite 数据，并校验 Git commit 和归档摘要。若检查不一致，应停止自动执行并提示版本冲突，而不是静默重建或覆盖仓库。

### 10.4 恢复

每次使用工作区前执行统一的 `ensureWorkspace`：

1. 获取会话对应的目标版本和 R2 快照。
2. 检查 Sandbox 中现有 workspace。
3. Agent 或平台读取 Git 状态并比较目标 commit。
4. 工作区已经匹配时直接继续。
5. 工作区缺失或不匹配时从 R2 解包完整快照。
6. 按项目配置恢复依赖和运行所需进程。
7. 校验 Git commit、SQLite 可用性和项目配置后执行用户工具调用。

恢复必须可重复执行，并能识别快照缺失、损坏、版本冲突和依赖恢复失败。

### 10.5 保存

一次平台版本保存包含：

1. 验证工作区变更和关键测试结果。
2. 创建本地 Git commit。
3. 停止应用对 SQLite 的写入并保证数据库状态一致。
4. 将整个工作区按忽略规则打包到 R2，包含 `.git` 和 SQLite。
5. 在 D1 中建立 version、commit、session 和 snapshot 的关系。
6. 将操作成功事件发送到会话界面。

R2 中的完整工作区快照属于持久备份；Cloudflare Sandbox 自带的备份恢复能力可作为短期 checkpoint。两者的内容可以相同，但前者由 atoms-lite 的版本模型长期管理。

- `versions`
- `artifacts`
- `snapshots`
- `previews`
- `exports`
- `deployments`

```text
projects/{projectId}/
```

## 12. 生成应用设计

### 12.1 默认原则

在用户没有提出多平台要求时：

- 使用普通项目结构和标准 Web API
- 使用单一的默认运行目标
- 不提前生成多个部署目录
- 不引入不必要的 adapter、抽象工厂和平台插件
- 优先保证应用可运行、代码可读和可导出

生成结果还应遵守默认体验基线：

- 用户未指定样式时，使用现代、克制且完整的视觉系统
- 不输出仅满足功能的低质模板页面
- 为常见空状态、错误状态、加载状态和移动端布局提供实现
- 对五子棋、任务看板等交互型应用提供真实状态变化和重置/操作反馈
- 对 PPT 提供一致的页面尺寸、主题、版式、层级和内容节奏
- 在声明完成前进行构建、打开预览或生成预览截图等验证

### 12.2 推荐边界

生成应用应避免直接依赖 atoms-lite 的内部服务。业务代码只通过公开且明确的配置访问：

- 数据库连接
- 对象存储
- 模型调用
- 运行时端口和地址

如果用户明确需要跨平台部署，则增加必要的薄适配层，而不是让界面、路由和业务逻辑包含平台判断。

### 12.3 开发数据库

生成应用在 Sandbox 中默认可以使用 SQLite：

- 数据位于 `/workspace/data/app.db` 或项目声明的路径
- schema 和迁移进入源码版本
- 临时测试数据可忽略
- 需要保留的应用数据必须纳入快照策略

生成项目应提供受控的 `.gitignore`，默认不提交：

- `node_modules` 和构建缓存
- 日志与临时文件
- `.env` 和本地密钥
- SQLite 的 WAL、SHM 和临时文件
- 默认临时测试数据库

atoms-lite 默认将需要保留的 SQLite 数据库随整个工作区快照保存，以便停止和恢复后继续操作。Git 仍只通过 `.gitignore` 控制源码仓库是否跟踪数据库文件；数据库随 workspace backup 保留，不等于进入 Git commit。

Git 仓库默认保留 schema、迁移、seed 定义和可复现数据状态所需的脚本。R2 工作区快照可以包含不进入 Git 的运行数据库，但快照恢复的是对应版本的完整工作区状态。

如果生成 Cloudflare 原生应用，本地也可通过 Wrangler 的 D1 local binding 使用 D1。不得在应用源码中将 SQLite 与 D1 的调用方式混用。

### 12.4 平台适配

“同一份业务代码、不同平台部署”要求适配器边界，而不意味着一个完全相同的构建产物适用于所有环境。

可选适配内容包括：

- Node.js HTTP 入口
- Cloudflare Worker 入口
- Vercel Serverless 入口
- SQLite、D1 或其他数据库驱动
- 本地文件系统、R2 或其他对象存储

只有用户明确提出相关部署需求时才生成对应适配器。

### 12.5 非 Web 产物

PPT 等文件产物可由 Sandbox 中的文档生成工具创建。其源码、导出文件与中间预览文件都属于版本关系的一部分：

- 可编辑源码优先进入源码快照。
- PPTX 进入 Artifacts 和 R2。
- 预览缩略图、PDF 或页面图片用于前端预览。
- 导出失败应明确返回，并保留生成日志。
- 用户可对同一 PPT 在后续会话中提出内容或风格调整。

文档产物与 Web 应用共用会话、版本和产物模型，但使用各自的生成器、验证器和预览器。

## 13. 安全边界

### 13.1 文件与命令

- 路径必须规范化并限制在 `/workspace`
- 禁止路径遍历和符号链接逃逸
- 命令须经过程序和参数策略检查
- 终止失控和超时进程
- 限制输出大小
- 禁止访问系统敏感目录

### 13.2 网络

- 默认允许受限的包安装和预览所需网络
- 禁止生成应用访问 atoms-lite 管理接口
- 不向 Sandbox 注入 OpenCode、Cloudflare 和平台管理凭据
- 外部网络权限必须可配置和审计

### 13.3 数据

- 项目和用户权限在进入 Sandbox 前完成校验
- 每次工具调用绑定用户、项目、会话和请求标识
- 版本和快照按项目隔离
- 敏感字段不进入模型消息和普通日志
- 对生成代码和用户输入均按不可信内容处理

## 14. 本地开发环境

本地运行环境包括：

- Next.js 前端开发服务
- Wrangler Worker
- 本地 D1
- 本地 R2 binding
- 本地 Durable Objects
- Podman 或其他兼容容器引擎启动的 Sandbox

Podman 兼容性依赖 Docker-compatible socket、镜像构建、volume、网络和 FUSE 行为，应在统一 SandboxAdapter 上保留 Docker fallback。

D1、R2 和 Durable Object 的本地状态使用 Wrangler 持久化目录；容器内源码则通过与生产一致的 R2 快照恢复流程进行验证。

## 15. 验收标准

### 15.1 核心闭环

以下过程必须可以完整执行：

1. 创建项目。
2. 输入需求。
3. Agent 检查当前工作区并生成代码。
4. 安装依赖、运行构建或测试。
5. 启动应用并显示预览。
6. 用户继续提出修改要求。
7. Agent 修改现有代码而不是无条件覆盖。
8. 保存新版本。
9. 恢复旧版本并可继续工作。
10. 导出当前版本源码。

### 15.2 持久化

- 页面刷新后会话仍然存在。
- Worker 重启后项目和版本仍可读取。
- Sandbox 停止后，工作区可以从 R2 恢复。
- 应用 SQLite 数据的持久化范围与用户提示一致。
- 用户可以切换多个项目内会话，并恢复各自消息、版本和产物。
- 同一项目的并发写操作不会发生无提示覆盖。
- 压缩不会删除原始消息、工具调用或角色历史。
- 会话恢复后可读取会话摘要和各角色摘要。

### 15.3 运行控制

- 用户可以取消 Agent 运行。
- 长命令达到超时后明确结束。
- 失败的工具调用显示原因。
- 预览进程空闲后可停止。
- 下一次工具调用会按需启动或恢复 Sandbox。

### 15.4 安全

- 项目 A 无法读取或修改项目 B 的文件。
- 生成代码无法读取平台凭据。
- 路径逃逸和未授权内部网络访问被拒绝。
- 高风险操作需要审批或受策略限制。

### 15.5 交付结果

至少分别验证以下场景：

- 生成并运行一个五子棋或类似的轻量交互应用。
- 生成并运行一个任务看板，完成增删改操作和数据持久化。
- 生成一个可下载、可进行页面预览的 PPTX。
- 在一个已有应用会话中继续修改，而不是重建全部代码。
- 从同一项目的不同会话查看或继续不同版本分支。

在用户仅描述功能、未提供设计稿时，结果仍应具备一致风格、清晰层级、完整交互状态和响应式表现，而不是普通脚手架或静态 mockup。

### 15.6 工作台体验

- 会话、预览、Sandbox 和 Artifacts 窗口均可访问。
- 首页只包含新会话入口、必要提示和历史会话列表。
- 主应用只有首页和会话页面，其他能力由会话页面面板承载。
- 当前模式、角色、运行状态、版本和预览目标清晰可见。
- Sandbox 日志和工具细节不会挤占主要对话与预览空间。
- Preview、Artifacts、Sandbox 和版本可在宽窄布局中切换。
- Markdown、代码文件、diff 和终端输出可安全渲染。
- 多角色模式可查看各角色状态并进入角色历史。
- 窗口布局适应桌面和较窄屏幕。
- 工作台不包含当前范围外的连接器、Theme、SEO 和广告内容。

### 15.7 需求准入

- 用户能看到 Agent 对需求的支持等级。
- 条件支持和超纲内容在执行前被发现并提示。
- 高成本执行前展示可交付范围、假设和不实现项。
- 模拟集成、演示数据和真实外部服务有明确标识。
- Agent 不会因页面可运行而宣称已支持百万用户或生产就绪。
- 对超纲需求能够提供可执行的原型范围和生产化差距。

## 16. 面试题适配性

如果面试题考察的是在有限时间内完成一个能够展示 Agent 创作能力的可运行 Demo，则 atoms-lite 的定义具备较强的针对性：

- **真实交互**：不是固定聊天回复，Agent 会真实读写文件、执行命令并启动结果。
- **可持久化**：D1、R2、版本和恢复机制覆盖会话、消息、代码与产物。
- **完整闭环**：从需求、修改、运行、验证、预览、版本到导出形成可演示链路。
- **工程深度**：展示 LangGraph.js 编排、Sandbox 工具、安全边界、异步运行和生命周期管理。
- **用户体验**：工作台聚焦会话、预览、执行环境与 Artifacts，符合当前 Agent 产品形态。
- **功能亮点**：多会话、单/多角色切换、任务看板和 PPT 产物能够构成直观演示。
- **视觉质量**：默认设计基线避免结果虽然能跑、但外观粗糙的问题。

同时需要控制演示范围：

- 单用户能够显著减少认证、多租户隔离和团队协作成本。
- 不做连接器、Theme 系统和 SEO，避免分散核心闭环。
- 多角色应先支持可用的顺序协作，不需要以复杂并行调度作为首次展示重点。
- 外部一键发布可以后置，但必须保留可导出、可运行预览和版本证明。
- PPT 和 Web 是不同验证链路；演示时可选择其一作为主场景，另一项作为扩展能力。
- 视觉模仿应限于界面组织与工作流参考，不复制 atoms.dev 品牌和无关产品内容。

综合而言，该范围符合“真实交互、持久化、完整闭环”的核心要求，并且有足够的架构与产品延展性。要避免的主要风险是把 Cloudflare、Sandbox、LangGraph、多角色和多类型产物全部同时做成最完整形态；面试演示应优先证明一个小型 Web 应用的端到端闭环，其他能力用于体现设计扩展能力。

同时，atoms-lite 不把“生成一个页面”包装成“已经支持任意规模系统”。在用户提出购物商店、百万用户等高复杂度要求时，系统应通过需求准入、假设确认和范围降级主动管理预期，这比勉强生成一个无法验证规模的应用更符合面试中对工程判断力的考察。
