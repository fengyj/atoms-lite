# POC-03 沙箱持久化与恢复

时间盒：**1.5 小时**。依赖 POC-02。

## 1. 要验证的假设

1. 容器停止后，工作区能完整恢复（文件、`.git`、SQLite、依赖）。
2. 恢复耗时、快照体积在演示可接受范围内。
3. 恢复后预览能自动拉起，不需要人工干预。
4. SQLite 恢复后数据一致（不丢最近写入、不损坏）。

## 2. 不在范围内

- 不做跨项目隔离验证（Phase 1 单项目）。
- 不做快照加密与权限（演示可接受）。
- 不做增量快照。

## 3. 三组对照实验

### 3.1 快照内容：带不带 `node_modules`

| 方案 | 快照体积 | 恢复耗时 | 结果 |
|---|---|---|---|
| A：包含 `node_modules` | 大 | 短 | ? |
| B：排除，恢复后跑 `pnpm install` | 小 | 长 | ? |
| C：排除，基础镜像预装依赖 | 中 | 最短 | ? |

按 D8，**第一阶段先用 A**，把 B/C 的数字测出来作为优化依据。

### 3.2 SQLite 一致性

在「写入进行中」和「写入完成后」两个时点分别快照，恢复后比对：

- 直接拷贝文件 vs `sqlite3 .backup`
- 是否执行 `PRAGMA wal_checkpoint(TRUNCATE)`
- 恢复后 `PRAGMA integrity_check` 是否 `ok`

### 3.3 恢复后的服务

- 预览进程是否自动重建（PID、端口、URL 都不能复用旧值）
- 环境变量是否注入成功
- 健康检查通过的时间点

## 4. 通过标准

- [ ] 停止 → 恢复后，工作区文件哈希清单一致（排除可再生目录）
- [ ] `.git` 可用：`git log` 能看到历史，`git status` 干净
- [ ] SQLite `integrity_check` 为 `ok`，行数与停止前一致
- [ ] 恢复后预览自动可访问，无需人工点「启动」
- [ ] 记录三个数字：快照体积、恢复耗时、恢复后首屏时间
- [ ] 「停止 / 恢复」是**可点击的动作**，不是等空闲超时

## 5. Plan B

| 失败点 | 降级 |
|---|---|
| 快照太大 / 太慢 | 排除 `node_modules`，改用恢复脚本安装；或延长空闲超时，减少恢复次数 |
| SQLite 数据不一致 | 改用 `.backup` API 而不是文件拷贝；写入前强制 checkpoint |
| 恢复后预览起不来 | 恢复流程末尾增加「显式启动预览」步骤，并在 UI 上显示进度 |
| 快照不可用 | 退化为「只保 git bundle + 依赖重装」；应用数据不保证跨容器存活，并在 UI 上明示 |

## 6. 产物

- 一份恢复流程的伪代码（步骤顺序 + 失败分支）
- 三个数字的记录表
- spike 删除：`rm -rf spikes/poc-03-persistence`

## 7. 风险

- **快照包含 `.git` 与 `node_modules` 时体积可能很大**，上传/下载会吃掉演示时间。必须先量。
- 「代码运行不算活动」：长时间的构建期间如果没有请求，容器可能被判定空闲。恢复测试时要覆盖这种情况。
- 不要在恢复流程里做 `git reset --hard`，恢复失败时应报错而不是静默重建。

## 结论

**通过。本地快照可用，且能跨 Worker 重启恢复。**

### 核心验证（2026-11-18）

```
1. /snapshot   → 写入 state.txt + SQLite(2 行) → snapshotContainer()
                 存 snapshotId 到 DO storage
2. 杀掉 wrangler + docker rm -f 容器（模拟实例回收）
3. 重启 wrangler
4. /restore    → 从 DO storage 读 snapshotId → start({ containerSnapshot })
```

结果：

```json
{
  "ok": true,
  "snapshotId": "c0aa7310-...",
  "state": "tok-1795001083713",   // 与快照前一致
  "db": "rows=4",                 // 与快照前一致
  "ms": 1617
}
```

| 指标 | 数值 |
|---|---|
| 快照大小（仅 node 基础镜像，无 node_modules） | **79.9 MB** |
| 快照耗时（热） | 1.36s |
| 快照耗时（冷，含建容器） | 3.23s |
| 恢复耗时（含容器启动） | 1.6s |
| 销毁耗时 | 135ms |
| SQLite（WAL checkpoint 后） | ✅ 行数一致 |

### 四个结论

1. **本地快照是真的。** `snapshotContainer()` + `start({ containerSnapshot: { id } })`
   在 `wrangler dev` 下可用，不需要远端服务。

2. **快照是整个 rootfs，不是单个目录。** 一个裸 node 镜像就 80 MB；
   带 `node_modules` 的真实项目会到数百 MB 甚至 GB。
   → 这直接支撑了之前的决策：**快照只用于"停机/恢复"，不能按版本存**；
   版本仍然是 git commit。

3. **snapshotId 必须落在 DO storage（或 D1）里。**
   存在内存里的话，Worker 一重启就丢了——这是最容易写错的地方。

4. **恢复成本可接受（1.6s）**，但恢复后预览进程需要重新拉起
   （POC-02 的 `ensureRunning` 逻辑），这部分要串进恢复流程。

### 尚未验证 / 已知风险

- 快照在本地由 Docker 管理；`docker system prune` 会清掉。
  线上由平台管理，行为不同，需在真机验证一次。
- 带 `node_modules` 的快照体积/耗时尚未测。按 80 MB 基线推算，
  500 MB 的项目快照可能在 5-10s，需要在 POC-04 里量。
- 多版本并发快照未测（Phase 1 单项目，可接受）。

### Plan B（未触发）

| 失败点 | 降级 |
|---|---|
| 线上快照不可用 | 用 `tar` 打包 `/workspace` → R2，恢复时解包；逻辑与快照等价，只是慢 |
| 快照太大 | 排除 `node_modules`，恢复后跑安装；或只快照 `/workspace` 子目录 |
| 恢复后预览起不来 | 恢复流程末尾显式调用 `ensureRunning`，UI 显示进度 |

---

## 设计结论（2026-11-18 决策）

采用**官方快照作为唯一恢复机制**，不实现依赖缓存层。

| 机制 | 用途 |
|---|---|
| **CF 快照**（`snapshotContainer`） | 唯一的恢复路径，包含整个 rootfs（含 `node_modules`） |
| **git commit** | 版本与代码历史，轻量，留在工作区内 |
| **按需打包** | 用户点「导出」时生成 zip，排除 `node_modules`，不进恢复链路 |

明确**不做**：pnpm store 缓存、预装基础镜像、安装加速。
理由：这些方案都绑定具体语言生态（JS 的 pnpm、Python 的 pip/uv、Go 的 module cache），
为一个 8h demo 维护多语言依赖缓存不划算。

### 接受的代价

- 快照体积随 `node_modules` 增长（估算 300MB~1GB），耗时 5-10s；UI 需要进度提示。
- 快照不可下载、不可迁移，因此**导出**必须单独实现（但只在用户主动操作时发生）。

### 已知风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 平台快照丢失（beta 行为、配额、事故） | 工作区与 `.git` 一起丢失 | 可选：定期 `git bundle` → R2（只保代码历史，几百 KB） |
| 快照 beta 转 GA 后收费 | 成本未知 | 该路径可整体关闭，退化为「导出后重建」 |
| 恢复后预览未启动 | 用户看到空白 | 恢复流程末尾强制 `ensureRunning` |

### 与「版本」的边界（必须遵守）

> 快照只代表**当前工作区状态**，不代表任何版本。
> 版本切换永远走 `git checkout`，禁止用快照回滚版本。
> 快照拍摄时机：空闲停止前、容器销毁前、高风险操作前；**不按版本拍**。
