# POC-07 可观测性

时间盒：**1 小时**。依赖 POC-06（需要先知道框架自己记了什么）。

目标：出问题时能在 30 秒内回答「这次运行到底做了什么、在哪一步失败」。

## 1. 要验证的假设

1. 一次完整运行可以被事后还原成时间线（模型调用、工具调用、耗时、错误）。
2. 记录手段不依赖 Cloudflare 控制台（本地 `wrangler dev` 也能用）。
3. 记录本身不会拖慢主流程、不会泄漏密钥。

## 2. 不在范围内

- 不做指标聚合、告警、看板。
- 不接第三方 APM。
- 不做生产级日志轮转与保留策略。

## 3. 最小设计

三层，从上到下：

| 层 | 内容 | 存在哪 |
|---|---|---|
| 用户可见 | 运行状态、阶段、错误摘要 | 对话流 / 面板状态 |
| 运行事件 | 工具开始/结束、文件变更、预览状态、版本创建 | DO SQLite 的 `run_events` 表（`seq` 单调递增） |
| 调试细节 | 模型请求 id、token 用量、工具参数摘要、退出码、耗时 | 同表，长字段单独列；敏感字段脱敏 |

必须能回答的问题：

- 这次运行调了几次模型、几次工具？
- 哪个工具最慢、失败了没有、错误是什么？
- 生成的文件有哪些、最后一次版本是哪个 commit？
- 总 token、预估费用。

## 4. 步骤

1. 定义事件 schema（与 contracts 的控制通道事件对齐）。
2. 在工具包装层统一记录：进入、退出、耗时、参数摘要、结果摘要。
3. 做一个 `/debug/run/:runId` 页面（或 CLI 脚本），把事件按时间排开。
4. 故意制造一次失败（工具报错 / 构建失败），检查能否定位到具体步骤。
5. 检查日志里是否出现密钥、完整 prompt、用户附件内容。

## 5. 通过标准

- [ ] 给定 `runId`，30 秒内能拿到完整时间线
- [ ] 失败运行能定位到「第几步、哪个工具、什么错误」
- [ ] 事件写入不阻塞主流程（异步或批量）
- [ ] 日志中无明文密钥、无完整上游响应体
- [ ] 单次运行的事件行数 < 200（避免写爆）

## 6. Plan B

| 失败点 | 降级 |
|---|---|
| 写库影响性能 | 改为 `console.log` 结构化 JSON，用 `wrangler tail` 看 |
| 事件太多 | 只记「工具级」与「运行级」，不记每个 token |
| 调试页面来不及做 | 提供一个脚本：按 runId 导出 JSON，人工看 |
| 无法拿到 usage | 只记 token 估算值，并标注 |

## 7. 产物

- 事件 schema 定义（进 contracts）
- 一个查看入口（页面或脚本）
- spike 删除：`rm -rf spikes/poc-07-observability`

## 8. 风险

- **日志不是越多越好**。目标用户是你自己，标准是「30 秒能定位」，不是「记录一切」。
- 不要把完整文件内容写进日志，体积和隐私都不可控。
