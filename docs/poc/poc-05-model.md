# POC-05 模型基线

时间盒：**1.5 小时**。无依赖，可随时插入。

这一项验证的不是 SDK，而是**模型行为**。它决定演示脚本能写多长，以及「生成失败」要不要成为演示的一环。

## 1. 要验证的假设

1. 目标模型能在一个工具循环内、稳定地产出**可构建**的小应用。
2. 工具调用参数可靠（不漏参、不幻觉工具名、不重复调用）。
3. 取消能真正中断，而不只是断开前端流。
4. 单次生成的成本与时长可控。

## 2. 不在范围内

- 不比较多个模型（只在明显不合格时才换）。
- 不调优提示词（用最小提示词测下限）。
- 不做多角色。

## 3. 固定任务

统一用同一句话，减少变量：

> 「做一个任务看板：可以新增、完成、删除任务，数据要保存下来，界面要好看。」

工具集固定为 5 个：`list_files` / `read_file` / `write_file` / `exec` / `finish`。

## 4. 记录表（跑 10 次）

| 指标 | 记录方式 |
|---|---|
| 是否一次构建通过 | `pnpm build` 退出码 |
| 步数 | 工具调用轮数 |
| 首 token 延迟 | 从发送到第一个 text delta |
| 总时长 | 从发送到 `finish` |
| 输入/输出 token | provider 返回的 usage |
| 单次费用 | 按单价换算 |
| 失败类型 | 漏参 / 错工具 / 死循环 / 构建失败 / 超步数 |

## 5. 通过标准

- [ ] ≥ 8/10 次产出可构建的应用
- [ ] 首 token < 3s
- [ ] 总时长 P50 < 120s
- [ ] 单次费用 P50 < $0.10
- [ ] 取消后 3 秒内不再有新的 token 或工具调用
- [ ] 不出现「同一文件连续重写 3 次以上」的死循环

任一不达标 → 触发 Plan B。

## 6. Plan B

| 失败点 | 降级 |
|---|---|
| 构建通过率低 | 收紧任务复杂度（先只做单页 CRUD，不做路由）；提示词里给固定技术栈与文件结构 |
| 步数过多 / 超时 | 降低 `stopWhen` 阈值，把「规划」拆成一次独立调用 |
| 工具参数不稳 | 减少工具数量，合并同义工具；参数全部走严格 schema + 校验失败时回喂错误 |
| 取消不生效 | UI 上把「停止」实现为「断流 + 后台标记取消」，并在下一次工具调用前检查取消标志 |
| 成本过高 | 缩短 system prompt，工具描述精简；开启 prompt caching |
| 完全不可用 | 演示改为「预置生成结果 + 现场改一个小需求」，把风险从生成转移到修改 |

## 7. 产物

- 一张 10 行的指标表
- 一份「演示脚本可用长度」的结论（例如：能稳定演示 2 轮修改）
- spike 删除：`rm -rf spikes/poc-05-model`

## 8. 风险

- **不要把「跑通一次」当成通过**。模型行为方差很大，必须 10 次。
- 记录使用哪个模型 ID 与参数（温度等），否则结论不可复现。
- 如果 provider 不支持 usage 返回，成本只能估算，要在文档里注明。

## 结论

**通过，但速度是主要约束。**

### 10 次基线（2026-11-18）

模型：`deepseek-v4.1-flash`（OpenCode Go，OpenAI 兼容端点）
任务：单文件 `index.html` 任务看板（新增 / 完成 / 删除 + localStorage）
工具：`write_file` / `list_files` / `finish`

| 指标 | 结果 |
|---|---|
| 成功调用 | **10/10** |
| 结构完整（HTML + JS + localStorage） | **10/10** |
| 写出 `index.html` | **10/10** |
| JS 语法检查通过 | **10/10** |
| 平均耗时 | **136s**（范围 106–180s） |
| 平均步数 | 3 |
| 平均工具调用 | 2（write_file + finish） |
| 平均 tokens | **39.7k** |
| 总消耗 | 10 次 ≈ 22.6 分钟，≈ 397k tokens |

逐次：

```
149s 120s 180s 162s 131s 124s 119s 129s 139s 107s
```

### 三条结论

1. **可靠性没问题**：10 次全部一次成型，没有漏参、错工具、死循环。步数固定为 3，说明模型对这类任务的分步策略很稳定。
2. **延迟是硬约束**：P50 ≈ 130s，最慢 180s。这意味着：
   - 演示时必须让用户看到阶段进度（读文件 / 写代码 / 构建 / 预览），不能只有一个转圈；
   - 首个可见结果应该在 60s 内出现，所以「先出最小可运行版，再迭代」比「一次生成完整应用」更适合演示。
3. **成本可算**：单次约 40k tokens。按目标模型单价换算即可（本表未计费）。

### 对演示脚本的建议

- 不要在台上等完整生成。先发需求，讲架构，回来正好看到预览。
- 准备一个「已完成」的项目作为开场，现场只演示**增量修改**（一次 20–40s），风险和时间都可控。
- 失败态也要演一次（构建失败 → Agent 修复），这比一路顺利更像真实产品。

### 未验证

- 多文件项目（Vite/Next）的生成质量与构建通过率。
- 工具数量增加到 10+ 时的选择准确率。
- 取消（abort）是否真的中断计费——需要单独探针，POC-06 覆盖。
